Summary

ASPIS is a set of LLVM passes that hardens programs against soft errors by duplicating the computation (EDDI and its variants) and by checking the control flow with signatures (CFCSS, RASM and others). The goals of the project were (1) to protect C applications with ASPIS, (2) to verify the protection with fault injection and (3) to integrate the applications into the ASPIS main branch for regression testing.

  • We wrote four small self-checking applications: AES-128 encryption, an FFT, Huffman compression and a PID speed controller.
  • We added them to the official test harness of ASPIS, which builds every test with 55 combinations of techniques. On the main branch the first version of the applications passed only 100 of the 220 builds: EDDI, sEDDI and FDSC, the techniques that duplicate the whole program, made all four crash. We found the bug in EDDI behind the crashes, isolated it in a five-line program and avoided it in our code. All the 220 builds now pass.
  • We injected faults with gdb, driven by a short script, after counting the executed instructions with valgrind, and ran 28,000 experiments that flip a bit in a register or invert a conditional jump, on six hardening configurations.
  • EDDI removes the silent data corruptions (SDCs) caused by register bit-flips: none in 2000 faults, against 2.11% in the unprotected programs, at 3.7 times the executed instructions. RASM detects 99.3% of the inverted branches, CFCSS only 62.5%. The campaign also revealed a bug in RASM: it did not check the blocks created by EDDI, so EDDI combined with RASM missed more inverted branches than RASM alone (9.70% of SDCs instead of 0.70%). We fixed it with a one-line change; with the fix the combination leaves no SDC in 2000 inverted branches.

The fix of RASM and the test entries are ready as two patches for the ASPIS repository, and the EDDI bug as a bug report (aspis-integration/). All the code, the raw results and the scripts that produce every table and figure are in the repository (Appendix A). The use of a large language model is declared in Section 8.

1. Background

1.1 Soft errors and software-implemented fault tolerance

A particle strike can flip a bit in a register or in a memory cell. The hardware is not damaged, but the program may compute a wrong result without noticing it (a silent data corruption, SDC), crash, or hang. Software-Implemented Hardware Fault Tolerance (SIHFT) protects programs that run on unprotected hardware by transforming their code. Data-flow techniques duplicate the computation and compare the two copies at selected points. Control-flow checking (CFC) techniques give each basic block a signature and check at run time that the blocks are executed in an order allowed by the control-flow graph.

1.2 ASPIS

ASPIS (Automatic Software-based Protection and Integrity Suite, from the Greek word for shield; Baroffio et al., ACM TODAES 2024) implements these transformations as passes on the LLVM intermediate representation (IR). Its driver, aspis.sh, compiles the sources to IR without optimisations, links them, and runs:

  1. FuncRetToRef: every function that returns a value gets a _ret version that writes the result through an extra pointer parameter, so that the two copies of the program can receive two copies of the result;
  2. a data protection pass. EDDI (Oh et al., 2002) duplicates every instruction and compares the two copies before stores, calls and branches; sEDDI does not compare before stores; FDSC compares only at the basic blocks that have several predecessors; REDDI hardens only the functions and globals annotated with to_harden and what they use;
  3. a control-flow checking pass. CFCSS (Oh et al., 2002) updates a run-time signature with an XOR at the entry of each block and compares it with the signature of the block. RASM (Vankeirsbilck et al., 2017) checks the signature at the entry of each block and, before leaving the block, adds a value that depends on the successor that is taken. ASPIS also offers inter-RASM and RACFED, variants of RASM;
  4. DuplicateGlobals, which keeps the duplicated global variables consistent.

Every hardened function f gets a version f_dup that takes each parameter twice and executes both copies of the computation; each global variable gets a _dup copy. When a check fails the program calls DataCorruption_Handler (data checks) or SigMismatch_Handler (signature checks), two functions that the application must define.

As an example, this is how EDDI transforms int scale(int v) { return v * g; }, where g is a global variable. The result is returned through a pointer (FuncRetToRef), every parameter comes twice (%0 and %2 are the two copies of v, %1 and %3 of the result pointer), every load and multiplication is executed twice, and the two results are compared before they leave the function:

define void @scale_ret_dup(i32 %0, ptr %1, i32 %2, ptr %3) {
VerificationBB:
  %4 = alloca i32                       ; v
  %5 = alloca i32                       ; its copy
  store i32 %2, ptr %4
  store i32 %0, ptr %5
  %6 = load i32, ptr %4
  %7 = load i32, ptr %5
  %8 = load i32, ptr @g
  %9 = load i32, ptr @g_dup
  %10 = mul nsw i32 %6, %8
  %11 = mul nsw i32 %7, %9
  %12 = icmp eq i32 %10, %11            ; consistency check
  br i1 %12, label %13, label %ErrBB
13:
  store volatile i32 %10, ptr %3        ; "return" both copies
  store volatile i32 %11, ptr %1
  ret void
ErrBB:
  call void @DataCorruption_Handler()
  unreachable
}

1.3 The test harness of ASPIS

The tests of ASPIS are listed in testing/config/tests.toml. The harness (pytest test.py in testing/) compiles each test with the 11 data protection options (none, EDDI and its variants --multiple-errbb and --coarse-grained, REDDI and the same variants, sEDDI, FDSC) combined with the 5 control-flow options (none, CFCSS, RASM, RACFED, inter-RASM), runs it, and compares its output with the output of the program compiled by clang++ without ASPIS. A test can exclude some techniques with a black_list.

2. The applications

We wrote four small applications representative of the code that runs on the embedded systems targeted by SIHFT. They follow the same rules:

  • they are deterministic and self-checking: they print a summary of their results, compare them with known answers and end with SUCCESS or FAIL (exit status 0 or 1);
  • they define the two fault handlers, which print FAULT_DETECTED: DataCorruption or FAULT_DETECTED: SigMismatch on stderr and exit with status 2 or 3, so that a detection is easy to recognise;
  • they are valid C and C++, because the harness compiles the reference program with clang++;
  • they are short: they execute less than a million instructions, so that thousands of fault injections take minutes;
  • they use only the C standard library and are released under the MIT license, so that they can enter the ASPIS repository.

3.2 A bug in EDDI

With a debugger we found that the faulting instruction was always an 8-byte store right after a call to printf, writing into a string literal, which is in read-only memory (.rodata): "kat ct: " in aes128, a label received as a parameter and printed with printf("%s", label), and the string chosen by ok ? "OK" : "MISMATCH" or ok ? "SUCCESS" : "FAIL" in the other three. The five-line program aspis-integration/reproducers/string_literal.c reproduces the crash:

static void show(const char *label) { printf("%s\n", label); }
int main(void) { show("hello"); return 0; }

Cause. When a hardened function calls a function that has no _dup version, like printf, the callee may write through its pointer arguments, and it updates only the original copy of the data. After the call EDDI therefore copies each pointed value from the original to the duplicate (fixFuncValsPassedByReference in passes/EDDI.cpp). The copy loads and stores a pointer-sized value (8 bytes), whatever the pointed type is. When the argument points to a string literal, the two copies of the pointer are the same read-only address (the two copies of the parameter label, or of the ?:), so the store makes the program crash. The fixed size of the copy is wrong in general too: it overflows objects smaller than 8 bytes and synchronises only the first 8 bytes of larger ones.

What we did. The applications now print only literal strings (printf("SUCCESS\n") instead of printf("%s\n", ok ? "SUCCESS" : "FAIL")), with the same output; a comment at the top of each file explains why. With this change all the 220 builds pass on the main branch (table above). We did not change EDDI: the bug is described, with the reproducer, the analysis and a possible fix, in aspis-integration/bug_report.md, ready to be reported to the maintainers.

3.3 No regressions

The only change to ASPIS of this project is the fix of RASM of Section 5.4. On the 48 tests that were already in ASPIS the harness gives exactly the same results with and without it:

4. Fault injection

4.1 Fault models

We emulate a single transient fault in the processor while the program runs its own code (never in the C library or in the dynamic loader, which ASPIS does not harden). An experiment picks a dynamic instruction uniformly at random, i.e. a random instant of the execution: an instruction with a probability proportional to the times it is executed, then one of its executions. It stops the program right before it and injects one fault:

  • register bit-flip (reg): one random bit of one of the 16 general purpose registers (rax … r15) is inverted;
  • inverted branch (branch): the instant is chosen among the executions of conditional jumps, and the jump goes to the successor that the condition did not select. This is the effect of a fault in the flags or in the branch unit, and the classic error that control-flow checking should detect.

4.2 Injecting the faults with gdb

We did not write an injector: the experiments use two standard tools, gdb and valgrind, driven by two short Python scripts.

  • Golden run. Each program runs once without faults under valgrind (callgrind), which counts how many times each instruction of the program is executed; objdump tells which ones are conditional jumps. The output of a normal run is the reference (the golden output).
  • Experiment. fault_injection/gdb_inject.py (72 lines, 45 of them code) runs inside gdb. It receives an instruction and one of its executions, the k-th, drawn from the counts of the golden run, and puts a breakpoint on that instruction with an ignore count of k-1, so that gdb stops the program right before the k-th execution (gdb disables address randomisation, so the addresses are the same in every run). For a register bit-flip it changes the register (set $rax = ...); for an inverted branch it executes the jump (stepi), sees where it went and moves the program counter to the other successor. Then the program continues, and a watchdog kills it if it does not end in time.

Each experiment is classified, in this order, as: hang if after the fault the program did not end within 20 times its normal run time (at least 1 s); crash if it was killed by a signal; detected (data) or detected (CFC) if one of the two handlers reported the fault; masked if its output and exit status are the same as in the golden run; SDC otherwise, which includes a wrong output and the program’s own check printing FAIL.

4.3 The campaign

fault_injection/campaign.py builds each application with each configuration, records its size, does the golden run and runs the experiments, four at a time. We used six configurations: the unprotected baseline (the same aspis.sh pipeline without transformations), EDDI, CFCSS, RASM, and EDDI combined with CFCSS and with RASM, built with ASPIS b66a090 plus our fix of RASM. For each application, configuration and fault model we injected 500 faults, drawn with a seed derived from the names: 24,000 experiments. To measure the effect of the RASM bug (Section 5.4), EDDI+RASM was also run with ASPIS b66a090 without the fix: 4,000 more experiments. Eleven register bit-flips were not injected, because the drawn execution does not exist: valgrind counts the few instructions of the PLT stubs, through which the programs call the C library, together with the calling instruction. They are left out; the other experiments are still uniform over the real executions. Each proportion is given with its 95% confidence interval (Wilson score interval).

5. Results

5.1 Cost of the protection

Size of the code (.text) and executed instructions relative to the baseline (geometric mean over the four applications), and number of consistency checks inserted by EDDI in the four applications.
configuration code size executed instructions consistency checks
baseline 1.00x 1.00x 0
EDDI 9.27x 3.74x 1283
CFCSS 1.58x 1.65x 0
RASM 1.99x 2.33x 0
EDDI+CFCSS 13.90x 5.46x 1283
EDDI+RASM 14.80x 5.95x 1283

Data duplication is the expensive part. EDDI executes 3.74 times the instructions of the unprotected program (geometric mean over the applications, between 3.56x and 4.12x): every instruction is executed twice, and each of its 1283 checks adds comparisons and a branch. The code grows much more than the execution (9.27x), because every function exists in up to four versions (original, _ret, _dup, _ret_dup), each check splits a block, and without optimisations every value goes through the stack. The control-flow techniques cost less: 1.65x the executed instructions for CFCSS and 2.33x for RASM. Combined with EDDI the costs add up: 5.46x with CFCSS and 5.95x with RASM.

5.2 Register bit-flips

configuration n masked detected (data) detected (CFC) crash hang SDC SDC 95% CI
baseline 1995 83.6 0.0 0.0 14.3 0.0 2.11 1.56–2.83
EDDI 2000 83.3 2.9 0.0 13.9 0.0 0.00 0.00–0.19
CFCSS 1997 85.1 0.0 3.0 11.1 0.1 0.75 0.46–1.24
RASM 1998 85.4 0.0 2.8 11.0 0.0 0.80 0.49–1.30
EDDI+CFCSS 2000 83.7 1.3 2.3 12.7 0.0 0.05 0.01–0.28
EDDI+RASM 1999 83.8 1.9 1.6 12.6 0.0 0.20 0.08–0.51

Register bit-flips are mostly harmless: in the unprotected programs 83.6% of them are masked (the register was not in use, or was overwritten before being read), 14.3% crash the program (for example a corrupted address) and 2.11% silently corrupt the output. EDDI leaves no SDC in 2000 faults: with 95% confidence its SDC rate is below 0.19%, more than ten times lower. Its checks detect only 2.9% of the faults, but these are the dangerous ones: a wrong value is caught before it reaches a store, a call or a branch. The control-flow techniques alone leave 0.75% (CFCSS) and 0.80% (RASM), since a signature only sees the bit-flips that change the path of the program. Combined with EDDI they leave one and four SDCs in 2000 faults (0.05% and 0.20%): with so few cases these rates cannot be told apart from that of EDDI alone, as the intervals overlap.

RASM 2000 0.0 0.0 99.3 0.0 0.0 0.70 0.42–1.17
EDDI+CFCSS 2000 2.5 36.3 53.5 0.0 0.0 7.70 6.61–8.95

Inverted branches are the most harmful faults: 79.3% of them corrupt the output of the unprotected programs, because the results depend on how many times the loops run and on which path the data-dependent branches take.

EDDI and CFCSS detect almost only the inversions of the jumps of their own checks. Counted on the golden runs with fault_injection/check_jumps.py, 76.3% of the conditional jumps executed by the programs hardened with EDDI belong to its checks, and 62.4% with CFCSS: an inverted check jumps to the error handler. These shares are close to their detection rates (77.2% and 62.5%). The inversions of the program’s own branches are not seen. EDDI compares the two copies of the condition before the jump, but then executes a single jump, so both copies of the data follow the wrong path; CFCSS only checks that the program follows an edge of the control-flow graph, and the wrong successor of a branch is an edge too. They leave 18.75% and 29.05% of SDCs.

RASM detects 99.3% of the inverted branches: before leaving a block it updates the signature using the same condition as the jump, so a jump in the other direction reaches a block that expects a different signature. All its 14 SDCs (0.70%) come from a single conditional jump of pid_control that is not a branch of the IR: in load_at, return (k >= 1200 && k < 1300) ? 1.5f : 0.0f; is a select between two floats, which the x86 back-end implements with a jump when it does not optimise. No technique working on the IR can see that jump. EDDI with CFCSS leaves 7.7% of SDCs; EDDI with RASM none, because EDDI duplicates the select too, and a wrong jump in one copy makes the two copies differ.

5.4 A bug in RASM, found by the fault injection

With ASPIS b66a090, without our fix, EDDI+RASM left 9.70% of SDCs with inverted branches, much more than RASM alone (0.70%), although it adds the checks of EDDI to those of RASM. With fault_injection/sdc_sites.py, which maps the SDCs to the instructions where the faults were injected and shows the successors of the jumps, we found that all the 194 SDCs happened at conditional jumps towards blocks that start by writing a constant into the signature of RASM, instead of checking it.

The cause is in RASM.cpp: a block whose name contains “verification” is treated as a block created by RASM itself, and its signature is reset to the expected value without a check. The test was meant for the blocks of RASM (RASM_Verification_BB), but it also matches the VerificationBB blocks created by EDDI, which are the successors of most blocks of a program hardened with EDDI. A jump into the wrong one of them re-synchronised the signature and went undetected:

  br i1 %8, label %VerificationBB2, label %VerificationBB3
VerificationBB2:                        ; created by EDDI
  store volatile i32 24, ptr %2         ; RASM resets the signature, no check

Fix (patch 0001). A one-line change: only the blocks whose name starts with RASM_ (and the landing pads of C++ exceptions) are exempted, so the VerificationBB blocks get the entry check like any other block. RACFED had the same code and is fixed in the same way. With the fix EDDI+RASM leaves no SDC among the 2000 inverted branches, and its signature checks detect 67.1% of them instead of 36.4%; the rest is detected by the checks of EDDI.

7. Limitations

  • The fault models cover the general purpose registers and the conditional jumps only. Faults in the floating-point registers (used by fft and pid_control), in memory, and multiple faults are not injected.
  • 500 faults per application and configuration give wide intervals on the rates of single applications (for example 1.1-3.6% for the register SDC rate of aes128); the pooled rates (2000 faults) are more precise.
  • We compare the cost with the executed instructions, not with the run time: the applications run for a few milliseconds, too little for precise time measurements.
  • The control-flow techniques work on the IR, so they cannot see the jumps created by the back-end, such as the one of the floating-point select in pid_control (Section 5.3); only data duplication catches them.
  • Our applications avoid the EDDI bug of Section 3.2 instead of fixing it, so they do not test that part of EDDI; the reproducer should become a test once the bug is fixed.

8. Declaration on the use of large language models

The supervisors allowed the use of AI tools (“you can do whatever you want with IA even the whole project”), asking to “declare in the final report whether you have used LLMs and for what purpose”. This project was carried out with extensive use of an LLM-based coding agent, Claude (Anthropic), through Claude Code. The agent was used for:

  • writing the applications and the fault-injection and analysis scripts;
  • running the experiments: building LLVM and ASPIS, the test harness, the fault-injection campaign;
  • debugging ASPIS: isolating the failures, writing the reproducer, finding the causes, writing the fix of RASM and the bug report of EDDI;
  • writing this report, its tables and figures.

The students defined the goals and the scope of the project, supervised the work, and are responsible for checking the results and the content of this report.
